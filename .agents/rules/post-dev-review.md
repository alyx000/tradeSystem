# 开发后代码审查（内部审查）

> 2026-11-02 用户明确要求：“以后内部审查就好了”。
> 后续仅使用当前会话内的独立审查，不再启动外部 Codex、companion 或其他外部审查服务，也不再为旧外部审查门请求授权。此规则替代旧“双门”流程；除非用户以后明确改变偏好，外部审查不属于完成条件。

## 触发条件

完成一轮实质性代码改动后触发：

- 修改3个或以上文件的业务逻辑。
- 引入新函数、新CLI命令、新DB表/列、新API路由。
- 涉及schema迁移、跨数据层/跨服务变更。
- 前端类型接口或核心契约变更。

纯文档、注释、格式化、单文件typo或单测试增改可免审查；仍须执行适用的验证和差异检查。

每个实质性阶段完成并通过测试后立即审查，不积压到最终收尾。必须同步修改才能工作的紧耦合生产方与消费方可合为一个审查单元。

## 第一步：按影响范围定档

| 档位 | 触碰范围 | 内部审查安排 |
|---|---|---|
| 重点审查 | schema/迁移；写入与状态流转；推送或调度出口；新增CLI/API/provider capability或共享类型；凭据/env读取路径 | 两名会话内独立审查者，可并行；分别检查正确性/边界与契约/副作用/测试覆盖 |
| 常规审查 | 纯渲染、报告文案、只读子命令、常量阈值、测试重构 | 一名会话内独立审查者 |
| 前端专项 | 纯UI且不涉及跨层契约 | 内部审查并覆盖UI行为、可访问性和显示验证 |

拿不准时按重点审查。各阶段分别定档，不因一个阶段风险较高而要求所有阶段使用相同安排。

## 第二步：内部审查与修复

- 后端业务改动审查前运行 `make check-scripts`；前端或跨层按 `dev-workflow.md` 执行对应验证。
- 可使用当前会话的审查子代理；只读取明确限定的改动及必要依赖，保护工作区中其他任务的修改。
- 独立审查覆盖bug、回归、边界、测试缺口、接口一致性、安全、复用及复杂度。
- 多名审查者并行期间不修改被审查代码；结果合并去重后统一处置、修复和复测。
- 不把主实现者自检冒充独立审查；环境缺少独立审查能力时如实说明覆盖限制，不自动切换外部服务。
- 纯方案级额外审查仅在用户明确要求时触发，不由本规则强制启动。

收到问题后由主会话判断和处置，不把整段审查意见转交用户代为裁决。反驳须有技术理由；不能为通过审查而作无意义改动。

## 第三步：结束条件

1. **严重问题全部解决且修后测试通过**。后端运行 `make check-scripts`，涉及前端另跑 `make check-web`；适用范围见 `dev-workflow.md`。不得用修复前的结果代替。
2. **中等问题逐条处置**：标为“已修”“反驳”或“defer”。反驳理由写入相关代码注释；defer说明原因与重新处理的触发条件。轻微问题至少在汇报中说明。
3. **最多两轮审查**。第二轮仍有严重问题时停止并交用户决策，说明问题、拟处理方式及无法解决的原因，不无限重跑。

内部审查与适用测试完成即可满足审查要求。外部审查未执行、不可用或曾被拒绝不再构成待办或阻塞项。

## 汇报格式

先给处置结论，再给简短依据：

```text
内部审查结论（重点 / 常规 / 前端专项）：
- [严重] 已修：问题与定位
- [中等] 已修并补测 / 反驳 / defer：结论及依据
- [轻微] 已修 / 接受为已知：结论

验证：
- make check-scripts：实际结果
- make check-web：适用时记录
```

省略不存在的严重度，不虚构问题、通过结果或已完成的审查。
